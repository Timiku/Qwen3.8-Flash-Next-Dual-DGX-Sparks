# Ported-runner A/B — 2026-09-20

Did the runner changes ported from the single kit move decode throughput?
Answer: no measurable change — the delta sits inside the session-to-session
band this kit's own rerun note (`rerun-20260916.md`) already warns is the only
reproducible quantity. The port is hygiene, not speed.

## Setup

Same harness, same framing as `rerun-20260916.md`: `bench/sweep.py` driving
sparkDash, 600 tokens, prose + code, S = 1/2/4/8, 3 repeats in alternating
order, `nvrm=0` every row. One `dual-base` tree is the pre-port boot, the kit
directory is the ported boot.

- **base** = `d2f54b7` checkout, `.env` with the ported-knob block stripped and
  the template back on `EXTRA_VLLM_ARGS`; stock `cudagraph_capture_sizes`,
  the 47k draft vocab *without* the 23 byte-pin rows, no `_CG_SIZES` splice.
- **port** = this kit's `start.sh` (commit `7d91b4c`): `CUDAGRAPH_CAPTURE_SIZES=auto`,
  the byte-pinned vocab, `CHAT_TEMPLATE` via the overlay, plus the non-decode
  changes (readiness, stop, sha256, supervision) which cannot touch a step time.
- Two port sessions (`port#1`, `port#2`) and one base session bracket the run;
  `port#2` additionally adds the odd-S cells S = 3/5.

The graph-shape knob is the only one that could move decode, and here it is a
non-change: the base's stock list `round_up`s to multiples of the verify width
`(1+K)=4`, so it captures `{4,8,16,24,32,…}` — every batch the scheduler builds
at `MAX_NUM_SEQS=8` (widths 4,8,16,32 for S=1,2,4,8) already has a graph in
*both* arms. `auto` only differs at the odd widths S=3/S=5, tested explicitly
below.

## Result — throughput, decode tok/s (mean of 3)

| cell | base | port#1 | port#2 | port-mean Δ |
|---|---|---|---|---|
| prose S=1 | 66.6 | 64.5 | 66.2 | −1.5% |
| code  S=1 | 83.1 | 80.6 | 81.7 | −2.3% |
| prose S=2 | 58.1 | 54.4 | 55.5 | −4.9% |
| code  S=2 | 73.1 | 68.6 | 68.9 | −5.2% |
| prose S=3 | —    | —    | 47.4 (base 47.6) | −0.3% |
| code  S=4 | 59.9 | 57.3 | 58.3 | −2.7% |
| prose S=4 | 44.1 | 44.2 | 43.4 | −2.3% |
| prose S=5 | —    | —    | 41.8 (base 40.6) | +3.0% |
| code  S=8 | 48.9 | 48.0 | 48.6 | −1.5% |
| prose S=8 | 35.4 | 35.1 | 34.6 | −1.5% |

Mean over the eight matched cells: **−3.2%** (`port#1`) / **−2.4%** (`port#2`),
consistent in sign but inside the per-cell noise `rerun-20260916.md` documents
(−5.0 to +3.6 point cell swings on a session where the *mean* moved +8.4%).
Acceptance per position is unchanged within noise (`prose S=1 0.85/0.65/0.50`
→ `0.86/0.65/0.47`), so this is not the byte-pin changing acceptance — the
byte-pin only adds rows that were frequency-losers before, and acceptance is
measurably identical, exactly as designed.

## Result — the two cells where the graph list actually differs

S=3 (width 12: base pads to 16, port captures 12 exact) and S=5 (width 20:
base pads to 24, port captures 20 exact). If the auto list bought anything,
these are where it shows:

| cell | base | port | Δ |
|---|---|---|---|
| prose S=3 | 47.6 | 47.4 | −0.3% |
| prose S=5 | 40.6 | 41.8 | +3.0% |

Flat to slightly favouring the port, both inside noise. The prefill-graph
padding at those widths is worth well under a percent here, as expected when
the padded-vs-exact batch is a handful of idle lanes on an already
memory-bound step.

## ms/step

No consistent port penalty once the sessions are paired (S=2 shows +5% in both
port runs — the one cell that repeats — but S=2 has an exact graph in both
arms, so it is not the capture list; it tracks the acceptance dip, not a
mechanism). The pool is identical (`5.60M` base → `5.60M`/`5.78M` port; the
`+180k` tok is page-cache state at boot, not the port).

## Caveats

1. The `code` prompt is the synthetic high-accept one `rerun-20260916.md`
   flags — saturation column, valid for the A/B sign only.
2. Two port sessions vs one base. The base was the 09-16 `tuned`-arm config
   re-derived as `d2f54b7`; it is a faithful pre-port boot but was not run
   twice.
3. Nothing here speaks to the changes that can't touch a decode step: graceful
   stop, `READY_TIMEOUT_S` hardening, `VERIFY_SHA256`, supervision, the
   byte-pinned vocab's correctness argument (drafts outside the subset are
   rejected exactly like any other bad draft). Those are validated by their own
   tests and the boot smoke, not a throughput sweep.

## Verdict

**Throughput-neutral within noise; the port is a hygiene and correctness
change, not a speed change.** Keep it for the supervision, the sha256 guard,
the graceful stop, and the byte-pinned vocabulary's correctness margin — not
for a decode gain. `CUDAGRAPH_CAPTURE_SIZES=auto` earns its default on
`MAX_NUM_SEQS≥10` or odd-`K` configs where the stock list genuinely leaves a
verify width without a graph; on this box's `MAX_NUM_SEQS=8, K=3` shape it is a
no-op by construction.
